## 4. Licence — DECIDED

**OTIlib is GPL-3.0, and GPL-3.0 is accepted for the research prototype.** That
is the project owner's decision and it is settled; nothing downstream should be
written as though it were still open.

What the decision does *not* do is make the backend mandatory. It stays **OFF by
default**, which is now an ARCHITECTURAL choice rather than a licensing hold:

```sh
cmake -S . -B build -DWARP_HYPAD_WITH_OTILIB=ON   # explicit opt-in
```

Three properties are maintained deliberately:

* **Optional.** The core library and every non-sensitivity gate build and pass
  without it, so a contributor who does not want the dependency can still run
  most of the suite. Verified continuously: the OTIlib-disabled configuration is
  part of the release check.
* **Isolated.** Nothing outside `include/warp_hypad/sensitivity/` may include an
  `oti/` header or name an `onumm3n2` symbol. Substituting a different AD
  backend means writing one more directory there and nothing else.
* **Externally pinned.** The checkout is not vendored into this tree. It is
  fetched by `scripts/bootstrap_otilib.sh` / `.ps1` at the recorded revision, and
  CMake verifies the SHA at configure time and fails hard on a mismatch. This
  keeps the repository free of a large upstream history while making the pin
  machine-checked rather than a comment.

## 5. Windows / MSVC compatibility — better than upstream documents

Upstream states the library works on "Windows (only working under WSL)". That is
true of the **full** build, which needs conda, Cython, and a `make gendata` step
producing precomputed sparse-direction tables.

It is **not** true of the static scalar types. Verified: no `dHelp` or
`precompute` reference exists anywhere under the static sources. Consequently:

- `onumm3n2` scalar compiles and links with `cl.exe` **unmodified**;
- no WSL (none installed), no conda (not on PATH), no Docker, no generated data;
- upstream's own `examples/c/basic_scalar.c` builds and runs natively.

The one adjustment needed is that OTIlib is a **unity-build** project: files
under `src/c/static/onumm3n2/` have no includes of their own and must be
`#include`d into one translation unit. Upstream's aggregator pulls in the array
path too, which drags in `oarrm3n2_*` symbols from other modules. warp_hypad has
its own containers and needs only the scalar type, so
`src/sensitivity/oti_onumm3n2_unity.c` includes the scalar half only. That is
what keeps the dependency to **3 compiled files**.

## 6. Selected scalar type

**`onumm3n2_t`** — 3 imaginary directions, truncation order 2.

```c
typedef struct {
  coeff_t r;                          // real
  coeff_t e1, e2, e3;                 // order 1
  coeff_t e11, e12, e22, e13, e23, e33;  // order 2
} onumm3n2_t;
```

Three directions is exactly the warp parameter set (velocity, radius, sigma);
order 2 yields the **full gradient and Hessian in a single evaluation**. Upstream
also ships `m1/m2/m3/m10 × n1/n2/n3/n4` and `m1 × n10/n20/n30`, so raising the
order or the parameter count later is a one-line change of type.

Note this is strictly better than anything available locally, all of which was
order 1.

## 7. Two API facts that would have silently corrupted results

Both were found by testing, not by reading — and both fail *quietly*.

**(a) `*_to` functions do not support output aliasing.** Calling
`onumm3n2_mul_oo_to(&x, &y, &x)` does not crash. It returns a correct real part
with **wrong derivatives**. My first integration test did exactly this and
returned `df/db = a²·cos(b)·sin(b)` instead of `a²·cos(b)` — off by a factor of
`sin(b)`, plausible enough to miss. Every operator in the wrapper therefore
writes to a fresh temporary, and `operator+=` is `*this = *this + rhs`.
`oti.aliasing_is_unsafe` locks this in as a regression guard.

**(b) OTI stores Taylor coefficients, not derivatives.** `e_ii = ½·∂²f/∂p_i²`,
while mixed `e_ij = ∂²f/∂p_i∂p_j` exactly. Reading the struct fields and calling
them "the Hessian" is wrong by a factor of 2 **on the diagonal only** — a bug
that leaves gradients perfect and keeps the Hessian symmetric. The adapter uses
the library's own `onumm3n2_get_deriv()`, which undoes the factorials.

A third would-be bug was caught by reading the source: seeding indices are
**0-based** (`set_im_r` → `set_item`, whose order-1 switch maps 0,1,2 → e1,e2,e3).
An initial `direction + 1` would have seeded the wrong parameter for directions
0 and 1 and written nothing for direction 2. `oti.seed_isolation` covers it.

## 8. Adapter design

```
include/warp_hypad/sensitivity/
├── otilib_scalar.hpp    OTIScalar + ScalarTraits specialisation
├── otilib_traits.hpp    aggregate include
├── otilib_seed.hpp      ParameterIndex, seed_parameter, seed_all
├── otilib_extract.hpp   extract_real/gradient/hessian
└── otilib_math.hpp      sqrt, exp, log, sin, cos, tan, sinh, cosh, tanh, pow
src/sensitivity/
├── oti_onumm3n2_unity.c scalar-only translation unit
└── otilib_adapter.cpp   parameter names
```

`OTIScalar` provides exactly what `TestScalar` provides and nothing more: no
ordering, no equality, no implicit conversion to `double`. So the Milestone 1
kernels compile against it **unchanged** — `Mat4`, `inverse`, the contractions,
all of it. No geometry code names an OTIlib symbol; nothing outside
`sensitivity/` includes an `oti/` header.

`abs()` is deliberately not exposed even though OTIlib provides it: `|x|` is not
differentiable at zero.

**Route chosen (Step 7 option 1): thin C++ wrapper over the C API.** Options 2–5
were rejected as unnecessary — the C API is directly wrappable, so generated
specialised types, procedural adapters, and source transformation all solve a
problem that does not exist here. The existing UMAT source-transformation
workflow in `OTI_LLM` was **not** recreated: it exists because Abaqus UMATs are
fixed-signature Fortran that cannot be templated. warp_hypad was written from
scratch with scalar-generic templates precisely so that direct substitution
works, and it does.

The **matrix-inverse derivative identity is the mandatory gate** for using OTI on
inverse metrics, and it passes at machine precision. It is a genuine Level D
check: the left side is AD propagated through the adjugate inverse, the right
side an analytic identity evaluated in ordinary `double` from separately
extracted pieces.

The FD comparison is intentionally held to a *floor*, not to machine precision.
The V-shape — error falling as O(h²) then rising as O(ε/h) — is itself the
evidence that FD is genuinely independent. Agreement at 1e-16 across all step
sizes would have indicated the reference shared a code path with OTI.

`oti.hessian_symmetry` passes but is explicitly recorded as **weak**: the Hessian
is symmetric by construction, since `(i,j)` and `(j,i)` read the same packed
coefficient. Kept only to document that it proves nothing.

Full suite: **9/9 CTest tests pass** (Milestone 1's 77 cases plus the OTI gate),
no regression.

## 10. Unresolved limitations

1. ~~Licence — the blocker.~~ **Resolved (§4).** GPL-3.0 is accepted for the
   research prototype. The backend remains optional, isolated behind the
   adapter, and externally pinned, which is an architectural choice and not a
   residual licensing question.
2. **Upstream test suite not run.** It requires the conda/WSL build. Upstream's
   own C example was run instead and verified against analytic values through
   order 3. Recorded honestly in `upstream_tests.txt` as a gap, not a pass.
3. **Direction count is fixed at compile time.** `onumm3n2` is 3 parameters. A
   fourth requires switching type and rebuilding — fine for the warp parameter
   set, worth knowing before the parameter list grows.
4. **Array/FEM paths of OTIlib are not built.** Only the scalar type. If matrix
   operations on OTI arrays are ever wanted, that pulls in the dense module.
5. **Thread safety not established.** Not investigated; the scalar type is a POD
   struct with no global state visible in the scalar path, but this has not been
   verified and matters before any parallel grid loop.
6. **`const_cast` in the wrapper.** OTIlib takes non-const pointers for pure
   inputs. Verified safe by behaviour for every operation used, not by upstream
   guarantee.
7. **Performance unmeasured.** `onumm3n2_t` is 10 doubles vs 1; the real cost
   ratio against `double` and against 3-parameter FD is a Milestone 9 question.

## 11. Recommendation

**Use OTIlib. Do not write a substitute.**

It is the authentic upstream by the same author as the local files, it builds
natively with MSVC contrary to its own documentation, it supplies gradient *and*
Hessian for the exact warp parameter set in one evaluation, and it passes the
matrix-inverse derivative identity at machine precision — the specific gate that
governs every curvature quantity in this project.

The GPL-3.0 question is **resolved** (§4): accepted for the research prototype,
with the backend optional, isolated behind the adapter, and externally pinned at
a CMake-verified revision. Everything else here is done and verified.
